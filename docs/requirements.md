## 概要と目的

Tangmen（唐門）は、x86\_64 向けの自作 OS カーネルを AI がゼロから実装するプロジェクトです。C 版の Kui（趙逵）、Rust 版の Yuzhu（郁竹）、未定の3言語目の順に、同じ仕様とテストで実装します。

目的は次の2つです。

1. **学習と趣味**：オーナーが OS の仕組みを、動くコードと解説書を通じて理解する
2. **生成 AI のコーディング能力の検証**：AI が人間と同じ道具でどこまでカーネルを書けるかを、記録を取りながら確かめる

| 区分 | ゴール | 判定 |
| --- | --- | --- |
| 当面の目標 | M6：シェルが動く | 自作シェルからコマンドを実行できる |
| 北極星 | M8：BusyBox が動く | Linux 用の静的リンク版 BusyBox（musl）が無改造で動く |

リポジトリ：[pyonkichi499/ai-kernel-bench](https://github.com/pyonkichi499/ai-kernel-bench)（公開、MIT）

## スコープ

対象は QEMU 上で動く x86\_64 のモノリシックカーネルと、その上で動く最小限のユーザーランドです。

**対象**

- カーネル本体：CPU 初期化、割り込み、メモリ管理、プロセス管理、システムコール、VFS とファイルシステム、TTY
- ドライバ：シリアル（UART 16550）、タイマー（Local APIC）、PS/2 キーボード、フレームバッファ、PCI、virtio-blk
- ユーザーランド：musl でビルドした自作シェルとテスト用プログラム、BusyBox
- 開発基盤：ビルド、Dev Container、テスト3層、CI、解説書、AI 記録
- 後からの置き換え：Limine から自作ブートローダーへ（UEFI → Multiboot2 → BIOS の順）

**スコープ外**（将来の発展候補として残す）

| 項目 | 外す理由 |
| --- | --- |
| ネットワーク（TCP/IP） | M8 までの目標に不要。単体で M7 並みの工数 |
| GUI、ウィンドウシステム | 同上 |
| サウンド | 同上 |
| USB | 仕様が大きい。virtio と PS/2 で代替できる |
| AHCI、NVMe など実機専用ドライバ | QEMU 中心の方針 |
| 32bit 対応 | x86\_64 のみ |
| 本格的なセキュリティ | 複数ユーザー、権限の厳密な管理、ASLR は扱わない（root のみ） |
| マルチコアの有効化 | M6 より前は扱わない。ロックは最初から入れる |

## 開発体制と AI の運用ルール

設計、実装、PR の作成、マージまでを AI が担い、オーナーは解説書とコードを読んで理解する役割です。

| 項目 | ルール |
| --- | --- |
| 実装 | AI がすべて実装する |
| 設計判断 | AI がすべて決める。理由は解説書に書き、オーナーは後から異論を出せる |
| PR | 基本はマイルストーン単位。大きいもの（M2、M3 など）は2〜3個に分ける |
| マージ | CI がすべて通ったら AI が squash マージし、マージ後に内容と解説書の場所を報告する |
| タグ | マイルストーン完了時に `c/m0`、`rust/m0` の形式で打つ |
| 理解の確認 | 解説書の確認問題は自習用。進行は止めない |
| 参照してよいもの | 学習済みの知識、仕様書（Intel SDM、UEFI、Limine プロトコル、ELF、man ページなど）、OSDev Wiki などの解説記事 |
| 参照しないもの | 既存 OS（Linux、xv6 など）のソースコード。読まないし、コピーもしない |
| 行き詰まったとき | 同じ問題で3セッション解決できなければオーナーに相談してよい。技術的なヒントは「人間の介入」として記録し、方針の確認は介入に数えない |
| モデル | 開始時は Claude Opus 5.5。切り替えはマイルストーンの区切りのみ。サブエージェントのモデルも記録する |
| ペース | 期限を設けない |
| 言語 | ドキュメント、コードコメント、コミット、PR はすべて日本語。専門用語は英語のまま |

## 技術要件

x86\_64、UEFI、Limine で起動するモノリシックカーネルを、Linux システムコール互換で作ります。

| 項目 | 要件 |
| --- | --- |
| アーキテクチャ | x86\_64 のみ |
| ファームウェア | UEFI のみ。QEMU では OVMF を使う |
| ブートローダー | Limine。バージョンを固定して取得する |
| ブート情報 | `boot/` 層がローダー固有の情報を独自の `struct boot_info` に変換する。カーネル本体は `boot_info` だけを参照し、Limine に直接依存しない |
| 初期状態の扱い | Limine が用意した GDT とページテーブルは仮のものとし、M1、M2 でカーネルが自分で作り直す。物理メモリの直接マップなど Limine 独自の約束事も `boot_info` に明示する |
| カーネル構造 | モノリシック |
| マルチコア | シングルコアで動かす。共有データには最初からロック（spinlock）をかけ、M6 以降にマルチコアを有効にできるようにする |
| システムコール | 最初から Linux x86\_64 互換。番号、`syscall` 命令による呼び出し規約、構造体の配置、errno を Linux に合わせる |
| ユーザー空間の libc | musl（静的リンク）。libc は自作しない |
| 実行環境 | QEMU（q35、KVM あり）。KVM がない環境では自動で TCG に切り替える |
| 実機 | M6 で画面コンソールを作った後、USB メモリからの起動を一度試す。動作は保証しない |
| 出力 | M0〜M5 はシリアルのみ。M6 でフレームバッファに画面コンソールを作り、色と ANSI エスケープシーケンスにも対応する |

## マイルストーン

M0 から M8 の9段階です。各マイルストーンは、完了条件を結合テストとして `tests/` に書き、そのテストが CI で通った時点で完了とします。細かい仕様は、各マイルストーンの解説書で AI が決めます。

| # | 名前 | 主な内容 | 完了条件 |
| --- | --- | --- | --- |
| M0 | 起動 | Dev Container、ビルド、Limine での起動、`boot_info`、シリアル出力、panic、テスト3層と CI の土台 | シリアルに起動メッセージが出る。CI でテスト3層がすべて実行される |
| M1 | CPU の基礎 | GDT、TSS、IDT、例外ハンドラ、Local APIC と I/O APIC、スタックトレース | 意図的に起こした例外を捕まえて内容を表示できる。タイマー割り込みが届く |
| M2 | メモリ管理 | 物理ページアロケータ、カーネル自前のページテーブル、カーネルヒープ（kmalloc） | 確保と解放のストレステストが通る。Limine のページテーブルから切り替え済み |
| M3 | マルチタスク | カーネルスレッド、コンテキストスイッチ、プリエンプティブなスケジューラ、spinlock、スリープと起床 | 複数スレッドが交互に動き、ロックで共有データが壊れない |
| M4 | ユーザーモード | ring 3 への移行、プロセスごとのアドレス空間、`syscall` 命令、Linux 互換の最初のシステムコール（write、exit など） | ユーザープログラムがシステムコールで文字を出して終了する。不正なメモリアクセスでカーネルが落ちない |
| M5 | プログラム実行 | ELF ローダ、VFS、initramfs（cpio）、ファイルディスクリプタ、open、read、close、brk、mmap（匿名） | musl でビルドした静的 ELF を initramfs から読み込んで実行できる |
| M6 | シェル | PS/2 キーボード、TTY、fork、execve、wait4、pipe、画面コンソール（色、ANSI 対応）、自作シェル | シェルからコマンドを実行し、パイプでつなげられる。実機でのお試し起動を一度行う |
| M7 | ストレージ | PCI の列挙、virtio-blk、ブロックキャッシュ、ext2 の読み書き | ディスク上の ext2 に書いたファイルが、再起動後も残っている |
| M8 | BusyBox | シグナル、ioctl（TTY）、getdents64、ファイルを対象にした mmap、時刻、その他 BusyBox が必要とするシステムコール | 静的リンク版 BusyBox の `sh` と、`ls`、`cat`、`echo`、`mkdir`、`rm`、`ps` など主要コマンドが動く |

ブートローダーを自作に置き換える作業（UEFI → Multiboot2 → BIOS）は、本線とは別の追加タスクとして扱い、実施時期は未定です。

## 非機能要件

実装からマージまで AI が行うため、品質はテストと機械的なチェックで守ります。

**テスト（3層）**

| 層 | 対象 | 実行方法 |
| --- | --- | --- |
| ホスト単体テスト | ハードウェアに依存しない部分（アロケータ、文字列関数、ELF パーサ、ファイルシステムの構造解析など） | 通常の Linux プログラムとしてビルドし、AddressSanitizer と UBSan を有効にして実行 |
| カーネル内単体テスト | ハードウェアに依存する部分（ページテーブル操作、割り込み、コンテキストスイッチなど） | テスト用カーネルを QEMU で起動し、結果をシリアルで報告 |
| 結合テスト | マイルストーンの完了条件、ユーザープログラムから見た振る舞い | 本番カーネルを QEMU で起動し、シリアル出力を検証。言語に依存しないので全言語の版で共通 |

**CI**

- GitHub Actions で M0 から運用する。Dev Container と同じイメージでビルドし、テスト3層をすべて実行する
- KVM が使えれば使い、なければ TCG で実行する
- 変更された言語のディレクトリだけをテストする。ただし共通部分（`spec/`、`tests/`、`user/`）が変わったら全言語をテストする
- マージ条件：CI がすべて通ること

**C 版のコーディング規約**

- clang、C17（C23 の機能は使わない）、`-ffreestanding`
- `-Wall -Wextra -Werror`
- clang-format で書式を揃え、CI でチェックする
- デバッグビルドではカーネル内でも UBSan を有効にする

**デバッグの仕組み**

- シリアルへのログ出力（レベル付き）
- panic 時にレジスタとスタックトレースを表示する
- `make debug` で QEMU を GDB 待ち受け状態で起動できる

**ドキュメント**

- マイルストーンごとの解説書（`docs/milestones/`）：仕組み、設計判断とその理由、コードの読み方、自習用の確認問題。実装の詳細ではなく「何をなぜそうしたか」を中心に書き、後の Rust 版の教科書にもする
- コード内のコメントは厚めに書く
- すべて日本語で書き、専門用語は英語のままにする

## リポジトリ構成とコード管理

1つのリポジトリで言語ごとにディレクトリを分け、仕様、テスト、ユーザープログラムは全言語で共通にします。

```
ai-kernel-bench/
├── .devcontainer/     # 開発環境（CI も同じイメージを使う）
├── .github/workflows/ # CI
├── docs/
│   ├── milestones/    # マイルストーンごとの解説書
│   ├── ai-log/        # AI 能力検証の記録
│   └── third-party.md # 外部ソフトとライセンスの一覧
├── spec/abi/          # システムコールなどの定義（ここから各言語のコードを自動生成）
├── boot/              # Limine の設定、起動イメージの作成
├── kernels/
│   ├── c/             # Kui（C 版）
│   ├── rust/          # Yuzhu（Rust 版）
│   └── <3言語目>/      # 未定
├── user/              # ユーザープログラム（musl でビルド、全カーネル共通）
├── tests/             # 結合テスト（全カーネル共通）
├── scripts/           # 外部ソフトの取得とビルド、QEMU 起動
└── Makefile           # make run KERNEL=c / make test KERNEL=rust / make test
```

| 区分 | 対象 | ルール |
| --- | --- | --- |
| 言語ごとに分ける | ソース、ビルド設定、ツールチェーンのバージョン指定、カーネル内単体テスト、ホスト単体テスト | `kernels/<言語>/` の中だけで完結し、独立してビルドできる |
| 全言語で共通 | 仕様、結合テスト、ユーザープログラム、起動イメージの作成、ドキュメント | 特定の言語に依存しない |
| 自動生成 | `spec/abi/` から作る C のヘッダと Rust のコード | 手で編集しない。定義を変えたら全言語のテストが通ることをマージ条件にする |

**Git の運用**

- `main` には常にテストが通る状態だけを置く
- 作業ブランチは `c/m1-interrupts` のように言語とマイルストーンを含める
- コミットメッセージは先頭に対象を付ける（`c: ページアロケータを実装`、`spec: write を追加`）
- 将来別リポジトリに分けたくなったら `git subtree split` で履歴ごと切り出せる

## 多言語の展開計画と命名

C 版が M6 に達したら Rust 版を始め、Rust 版が M6 に達したら3言語目を始めます。先行する言語の M7、M8 は、後続の言語と並行して進めます。

（図：多言語の展開順序。3 言語、2 つの切り替え点。期間は縮尺どおりではない。図は正本を参照）

各言語の版は『活俠傳』のキャラクターから名前を取ります。コードやファイル名では小文字（`kui.elf`）、表示では先頭だけ大文字（`Kui`）にします。

| 対象 | 名前 | モデル |
| --- | --- | --- |
| プロジェクト全体 | Tangmen | 唐門（物語の舞台となる門派） |
| C 版 | Kui | 趙逵 |
| Rust 版 | Yuzhu | 郁竹（鉄を打つ鍛冶屋で、Rust＝錆と掛けている） |
| 3言語目 | 未定 | 言語を選ぶときに決める |

**並行開発のルール**

- `spec/abi/` は1つの定義から全言語のコードを自動生成し、片方だけが変わる状態を作らない
- 仕様を変更する PR は、その時点で存在する全言語のテストが通ることをマージ条件にする
- 後続の言語は、先行する言語の解説書と結合テストをそのまま使う

## AI 能力検証の記録

AI がどこまで自力で書けたかを後から評価できるように、AI が PR ごととマイルストーンごとに `docs/ai-log/` へ記録します。オーナーの作業は増えません。

| 記録項目 | 内容 |
| --- | --- |
| モデル | 使ったモデルとバージョン。サブエージェントやワークフローで使ったモデルも含む |
| 作業量 | セッション数、おおよその時間、PR 数、コード行数 |
| テストの失敗 | CI が失敗した回数、修正にかかったやりとりの回数 |
| バグ | AI が作り込んだバグの内容、どのテスト層で見つかったか、すり抜けて後のマイルストーンで見つかったか |
| 行き詰まり | 解決に複数セッションかかった問題、自力で解決できなかった問題 |
| 人間の介入 | オーナーから受けた技術的なヒントと、その影響。方針の確認は含めない |
| 参照した資料 | 仕様書や解説記事の名前と URL |

言語間（C、Rust、3言語目）やモデル間で、同じマイルストーンを比べられる形式で残します。公開リポジトリの README には、検証の条件の要約とこの要件定義書へのリンクを載せます。

## ライセンスと外部ソフトウェア

リポジトリは MIT ライセンスを保ちます。そのため、GPL のコードとバイナリはリポジトリに入れません。

| ソフト | ライセンス | 扱い |
| --- | --- | --- |
| Limine | BSD | バージョンを固定して取得。`limine.h` はライセンス表記ごと同梱してよい |
| musl libc | MIT | バージョンを固定して取得し、ビルドする |
| BusyBox | GPLv2 | ビルド済みバイナリはリポジトリに置かず、スクリプトで毎回取得してビルドする |
| OVMF | BSD | Dev Container のパッケージから使う |
| 画面コンソール用フォント | 未定 | M6 でパブリックドメインか MIT 相当のものを選ぶ |
| Linux | GPLv2 | 仕様の確認には man ページや仕様書を使い、ソースは読まないし、コピーもしない |

使っている外部ソフトとそのバージョン、ライセンスは `docs/third-party.md` に一覧で残します。

## 工数見積

AI が実装する場合、C 版を M6 まで作るのにかかるのは約70〜110 時間、M8 までで約120〜210 時間と見積もります。人間が自分で書く場合の見積もりをもとに、その約1/3 として算出した概算です。

| 対象 | 人間が書く場合（時間） | AI が実装する場合の概算（時間） |
| --- | --- | --- |
| C 版 M0〜M6 | 200〜330 | 70〜110 |
| C 版 M7〜M8 | 160〜300 | 50〜100 |
| Rust 版 M0〜M8 | 200〜400 | 70〜130 |
| ブートローダーの自作置き換え | 70〜130 | 25〜45 |
| 3言語目 | 言語が決まったら見積もる | — |

- 時間の大半はデバッグです。特に M3（コンテキストスイッチ）と M8（互換性の細部）はぶれやすいです。
- オーナーが解説書とコードを読む時間は含めていません。ペースを決めない方針なので、暦上の期間も見積もっていません。
- 実際の作業量は `docs/ai-log/` に記録するので、この見積もりと比べられます。

## 開発環境と未決事項

開発は WSL2 上の Dev Container で行い、QEMU、clang、GDB、OVMF はすべてコンテナに入れます。

| 項目 | 状況（2026-10-04 時点） |
| --- | --- |
| ホスト | WSL2（Linux 6.18）。Docker 29.1 を使用可能 |
| KVM | `/dev/kvm` はあるが、ユーザーが `kvm` グループに未所属 |
| コンテナに入れるツール | QEMU、OVMF、clang、lld、GDB、clang-format、xorriso、make。Rust 版の開始時に Rust ツールチェーンを追加 |
| GitHub | 公開リポジトリ。GitHub Actions は無料枠で使える |

**オーナーの作業**

- [ ] `sudo usermod -aG kvm hiroshi` を実行し、WSL を再起動する（Windows 側で `wsl --shutdown`）

**未決事項**（決める時期に決める）

- 3言語目の言語とカーネル名：Rust 版が M6 に達したとき
- 自作ブートローダーの名前と着手時期：着手するとき
- 画面コンソール用フォント：M6
- 各マイルストーンの設計（メモリ配置、スケジューラ、ファイルシステムなど）：AI が各マイルストーンで決め、解説書に書く
