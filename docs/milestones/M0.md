# M0 解説書：起動（C 版 Kui）

M0 では、**何もない状態から「カーネルが起動して、シリアルに自分の状態を報告し、テストで検証される」ところまで**を作りました。
以降のマイルストーンはすべてこの土台の上に積み上がります。

この解説書は「何をなぜそうしたか」を中心に書いています。後で Rust 版（Yuzhu）を作るときの教科書にもなるよう、
C 固有の話と、言語に依存しない OS の話を分けて説明します。

---

## 1. 何ができるようになったか

`scripts/dev make run` で起動すると、シリアルに次のように出力されます（KVM あり、QEMU のメモリ 256MiB の例）。

```text
Kui 0.0.1 (Tangmen C kernel)
bootloader: Limine 11.2.1
cmdline:
hhdm: 0xffff800000000000
kernel: phys 0xa316000 virt 0xffffffff80000000
rsdp: 0xfb7e014
framebuffer: 1280x800 32bpp
memmap: 34 entries, 216472 KiB usable
  [0x0000000000000000, 0x0000000000087000) usable
  [0x0000000000087000, 0x0000000000088000) bootloader-reclaimable
  ...（中略）...
  [0x000000000a316000, 0x000000000a320000) kernel-and-modules
  ...（中略）...
  [0x00000000ffc00000, 0x0000000100000000) reserved
kui: init complete
```

| 行 | 意味 |
|---|---|
| `bootloader` | 起動したブートローダーの名前とバージョン |
| `cmdline` | カーネルに渡されたコマンドライン（M0 では自己テストの指定に使う） |
| `hhdm` | 物理メモリ全体が、この仮想アドレスから始まる範囲に写されている（後述） |
| `kernel` | カーネルが置かれた物理アドレスと仮想アドレス |
| `rsdp` | ACPI（ハードウェア構成の表）の入口。M1 で割り込みコントローラを探すのに使う |
| `framebuffer` | 画面の情報。M6 で画面コンソールを作るまでは使わない |
| `memmap` | 物理メモリのどこが使えるか。M2 のメモリ管理の出発点 |

このほか、異常を検出する仕組みが働くことも確かめられるようになりました。

```text
# コマンドライン selftest=ubsan（未定義動作をわざと起こす）
UBSAN: add-overflow at src/kmain.c:74:26
  'int32_t' (aka 'int')
PANIC: undefined behavior detected (add-overflow)
  called from 0xffffffff80003e42

# テスト用カーネル kui-ktest.elf（カーネル内単体テスト）
ktest: running 14 tests
ktest: PASS boot_info_basic_fields
...
ktest: 14 passed, 0 failed        ← この後 QEMU が終了コード 33（成功）で終わる
```

## 2. 起動の流れ

```mermaid
flowchart LR
    A[電源 ON] --> B["UEFI ファームウェア<br/>(QEMU では OVMF)"]
    B -->|ISO の EFI/BOOT/BOOTX64.EFI| C[Limine]
    C -->|limine.conf を読み<br/>kui.elf をメモリに配置| D["_start<br/>src/boot/limine.c"]
    D -->|Limine の情報を<br/>boot_info に詰め替え| E["kmain<br/>src/kmain.c"]
    E --> F[情報を表示して停止]
```

1. **UEFI**：電源が入ると、マザーボード上のファームウェアが起動します。QEMU では OVMF という UEFI 実装を使います。
   UEFI は起動ディスク（ここでは ISO）の `EFI/BOOT/BOOTX64.EFI` を探して実行します。
2. **Limine**：`BOOTX64.EFI` の正体は Limine です。設定ファイル `boot/limine/limine.conf`（ISO 内のパス。
   元はリポジトリの `boot/limine.conf`）を読み、`kui.elf` をメモリに読み込みます（テスト時の設定の差し替えは 11 章）。さらにページテーブル（仮想メモリ）を用意し、CPU を 64 ビットモードにしてから、
   カーネルの入口 `_start` へジャンプします。
3. **`_start`**（`src/boot/limine.c`）：まずシリアルポートを使えるようにします。これで、この先で何が起きても報告できます。
   次に、Limine から受け取った情報をカーネル独自の `struct boot_info` へ詰め替えて、`kmain` を呼びます。
4. **`kmain`**（`src/kmain.c`）：`boot_info` を表示し、コマンドラインで指定された自己テストを実行します。
   最後に `kui: init complete` を出して CPU を止めます。

## 3. Limine プロトコルの要点

Limine とカーネルの間の約束事を「Limine ブートプロトコル」といいます（仕様書は limine-protocol リポジトリの `PROTOCOL.md`）。

### リクエストとレスポンス

カーネルは、欲しい情報ごとに**リクエスト構造体**をバイナリの中に置いておきます。
Limine は起動前にカーネルのバイナリを走査してリクエストを見つけ、対応する**レスポンス**へのポインタを書き込みます。

```c
// src/boot/limine.c（抜粋）
LIMINE_REQUEST struct limine_hhdm_request hhdm_request = {
	.id = LIMINE_HHDM_REQUEST_ID,   // 「HHDM の情報をください」という識別子
	.revision = 0,
};
// 起動後: hhdm_request.response->offset に値が入っている
```

- **`id`**：リクエストの種類を表す 4 つの 64 ビット値（マジックナンバー）
- **`response`**：Limine が書き込むポインタ。対応していない機能なら NULL のまま
- **`volatile`**：Limine が外から書き換えるので、コンパイラに「値は変わらない」と最適化させないための指定
- **`used`**：コードから参照されていなくても、リンカに消させないための指定

Kui が出しているリクエストは、bootloader_info、executable_cmdline、hhdm、memmap、executable_address、rsdp、framebuffer の 7 つです。

### ベースリビジョンとマーカー

- **ベースリビジョン**：プロトコルの版です。Kui は最新の **6** を要求します（`LIMINE_BASE_REVISION(6)`）。
  Limine が対応していれば、3 番目の値を 0 に書き換えてくれます。`_start` は `LIMINE_BASE_REVISION_SUPPORTED` でこれを確認し、
  非対応なら `PANIC: boot: ...` を出して止まります。
- **開始マーカーと終了マーカー**：Limine は、2 つのマーカーの間だけを探してリクエストを見つけます。
  リンカスクリプトで、開始マーカー、リクエスト群、終了マーカーの順に並べています（5 章）。

### HHDM（Higher Half Direct Map）

Limine は、**物理アドレス p を仮想アドレス `p + hhdm_offset` で読み書きできる**ようにページテーブルを用意してくれます。
これが HHDM です（今回の値は `0xffff800000000000`）。ページングが有効な CPU は物理アドレスを直接扱えないので、
物理メモリに触るときはこの写しを使います。

注意点として、フレームバッファのアドレスと、ベースリビジョン 4 以降の RSDP のアドレスは、**HHDM 上の仮想アドレス**で渡されます。
`boot_info` には物理アドレスで持たせる方針なので、変換層で `hhdm_offset` を引いています。

### `_start` に来たときの CPU の状態（x86_64）

| 項目 | 状態 | Kui での意味 |
|---|---|---|
| CPU のモード | 64 ビットモード（ロングモード） | 16 / 32 ビットからの切り替えは Limine が済ませている |
| ページング | 有効（Limine のページテーブル） | M2 で自前のものに切り替える |
| 割り込み | 禁止（IF=0） | IDT（割り込み表）がまだないので、禁止のままにしておく |
| IDT | なし（base 0, limit 0） | M1 で作る |
| GDT | Limine が用意した仮のもの | M1 で作り直す |
| SSE / x87 浮動小数点 | 無効（CR0 / CR4 の該当ビットが 0） | 使うと例外になる。だからコンパイラに使わせない（6 章） |
| スタック | 64KiB 以上 | M3 でスレッドごとのスタックを用意するまでは、これを使う |

## 4. `boot_info`：ブートローダーに依存しないための抽象化

要件定義で「後からブートローダーを自作に置き換えられるようにする」と決めました。
そのため、**カーネル本体は Limine を知らず、`struct boot_info` だけを見る**構造にしています。

```text
  ┌──────────────────────┐
  │ Limine               │──→ src/boot/limine.c ──┐
  └──────────────────────┘     （変換層）          │      struct boot_info
                                                  ├──→  （kui/boot_info.h）  ──→ kmain()
  ┌──────────────────────┐                        │
  │ 将来の自作ローダー    │──→ src/boot/xxx.c ─────┘
  └──────────────────────┘
```

`#include <limine.h>` しているのは `src/boot/limine.c` だけです。

| フィールド | 中身 | 方針 |
|---|---|---|
| `bootloader` | 名前とバージョン | 表示用 |
| `cmdline` | コマンドライン | 静的領域へコピー（最大 256 バイト） |
| `hhdm_offset` | 物理メモリ直接マップの開始 | Limine 独自の約束事なので、暗黙にせず明示する |
| `kernel_phys_base` / `kernel_virt_base` | カーネルの配置 | M2 で自前のページテーブルを作るときに必要 |
| `rsdp_phys` | ACPI の入口 | 物理アドレスで持つ |
| `framebuffer` | 画面の情報 | 物理アドレスで持つ |
| `memmap[]` | 物理メモリの地図（最大 256 件） | 静的領域へコピー。種類は独自の `enum mem_type` に変換 |

設計上のポイントは3つです。

- **アドレスは物理で持ちます。** 仮想アドレスは「どんなページテーブルを使っているか」に依存します。そのページテーブルは M2 でカーネル自身のものに変わります。
- **コピーして持ちます。** Limine が用意したデータは `bootloader-reclaimable`（後で再利用してよい）領域にあります。M2 以降にそこを再利用すると、元のデータは壊れます。
- **知らないメモリ種別は `reserved` に倒します。** 未知の領域を「使える」と誤認するほうが危険だからです。

## 5. リンカスクリプトと higher-half カーネル

`kernels/c/linker.ld` は、カーネルを**仮想アドレスの最上位 2GiB（`0xffffffff80000000` 以降）**に置きます。
このようにアドレス空間の上半分にカーネルを置く方式を「higher-half カーネル」と呼びます。

```text
仮想アドレス空間（64 ビット）
0x0000000000000000 ┌────────────────────┐
                   │ ユーザー空間         │  ← M4 以降、ユーザープログラムが使う
0x00007fffffffffff ├────────────────────┤
                   │ （使えない穴）       │
0xffff800000000000 ├────────────────────┤
                   │ HHDM（物理メモリの写し）│
                   │        ...          │
0xffffffff80000000 ├────────────────────┤
                   │ カーネル（Kui）      │  text / rodata / data
0xffffffffffffffff └────────────────────┘
```

上半分に置く理由は、下半分を丸ごとユーザープログラムに明け渡せることです。
また、どのプロセスのページテーブルにも同じカーネルの写しを置けます。

**`-mcmodel=kernel`** は、「このコードは最上位 2GiB に置かれる」という前提でコンパイラに命令を選ばせるオプションです。
アドレスを 32 ビットの符号付き値（負の数）として埋め込めるので、短く速い命令が使えます。

### セグメントと権限（PHDRS）

```text
text    PT_LOAD  R-X  .text            コード（実行可・書き込み不可）
rodata  PT_LOAD  R--  .rodata .ktests  定数・文字列・テスト記述子
data    PT_LOAD  RW-  .data .bss       変数・Limine リクエスト
```

Limine はこの権限どおりにページを割り当てます（実行禁止の NX ビットも有効）。
そのため、「コードを誤って書き換える」「データを実行してしまう」といったバグは、その場で例外として止まります。
権限はページ（4KiB）単位でしか付けられないので、セグメントの境界を `ALIGN(CONSTANT(MAXPAGESIZE))` でそろえています。
リンク時の `-z max-page-size=0x1000` で、ページサイズを 4KiB にしています。

Limine のリクエストは、レスポンスのポインタを書き込まれるので、`data`（書き込み可能）に置いています。

## 6. コンパイラフラグの理由

カーネルはアプリケーションとは違う環境で動くので、多くのフラグが必要です（`kernels/c/Makefile`）。

| フラグ | 理由 |
|---|---|
| `--target=x86_64-unknown-none-elf` | OS なし（none）の x86_64 向けにコンパイルする。ホストの Linux 向けの前提（libc など）を持ち込まない |
| `-std=c17` | 要件で決めた C の規格 |
| `-ffreestanding` | 「標準ライブラリがない環境」と宣言する。`main` から始まる前提や、libc の関数があるという前提が外れる |
| `-fno-stack-protector` / `-fno-stack-check` | スタック保護は libc の仕組み（`__stack_chk_fail` など）に依存するので外す |
| `-fno-PIC -fno-pie` | 位置独立コードにしない。決まったアドレス（higher-half）に置くので不要で、余計な間接参照が減る |
| `-mcmodel=kernel` | 最上位 2GiB に置く前提のコードにする（5 章） |
| `-mno-red-zone` | 下記のコラム参照 |
| `-mno-mmx -mno-sse -mno-sse2 -mno-80387` | SIMD や浮動小数点のレジスタを使わせない。起動直後は無効で、使うと例外になる。また M1 以降、割り込みのたびにこれらのレジスタを保存する手間を省くため |
| `-fno-omit-frame-pointer` | フレームポインタ（rbp）を残す。M1 でスタックトレース（どの関数から呼ばれたか）をたどるのに使う |
| `-Wall -Wextra -Werror` | 警告をすべてエラーにする。AI が実装するので、機械的に検出できるミスは全部止める |
| `-O2 -g` | 最適化しつつ、デバッグ情報も残す（GDB や addr2line で使う） |
| `-fsanitize=undefined`（debug のみ） | UBSan（10 章） |

> **レッドゾーンとは**：x86_64 の通常の呼び出し規約では、関数がスタックポインタより下の 128 バイトを、
> スタックポインタを動かさずに一時領域として使ってよいことになっています。これを「レッドゾーン」と呼びます。
> ところがカーネルで割り込みが起きると、CPU は今のスタックにそのまま割り込みの情報を積みます。
> すると、レッドゾーンに置いていたデータが上書きされてしまいます。M1 で割り込みを有効にする前から、外しておきます。

リンクは `ld.lld -nostdlib -static -z max-page-size=0x1000 -z noexecstack -T linker.ld` です。
標準ライブラリを一切リンクせず、リンカスクリプトどおりに配置します。

## 7. シリアルポート（`src/drivers/serial.c`）

最初の出力先として、**シリアルポート（UART 16550 互換、COM1）**を使います。
画面に文字を描くにはフォントの描画が必要ですが、シリアルは「1 バイト書けば 1 文字送られる」だけなので、最も簡単です。
QEMU ではシリアルをホストの端末やファイルにつなげられるので、自動テストでも出力を読めます。

### I/O ポート

x86 には、メモリとは別に **I/O ポート**という 16 ビットのアドレス空間があり、`in` / `out` 命令で読み書きします
（`include/kui/arch/x86_64/io.h` の `inb` / `outb`）。COM1 のレジスタは、ポート `0x3F8` から始まる 8 個です。

### 初期化の手順（`serial_init`）

| 手順 | 書き込み | 意味 |
|---|---|---|
| 1 | IER ← 0x00 | 割り込みは使わない |
| 2 | LCR ← 0x80 | DLAB=1：次の 2 つのポートが「分周比」の設定になる |
| 3 | 分周比 ← 1 | 115200 / 1 = 115200bps |
| 4 | LCR ← 0x03 | DLAB=0、8 ビット、パリティなし、ストップビット 1 |
| 5 | FCR ← 0xC7 | FIFO を有効にしてクリア |
| 6 | MCR ← 0x1E、0xAE を送って読み返す | **ループバック検査**（下記） |
| 7 | MCR ← 0x0F | 通常モードに戻す |

**ループバック検査**は、UART を「送ったものがそのまま受信側に戻る」モードにして、1 バイト送って読み返すものです。
同じ値が返ってこなければ、ポートは存在しないとみなします。最近の実機にはシリアルポートがないことが多いです。
その場合、存在しないポートの「送信バッファが空いた」ビットを永遠に待ち続けて固まってしまいます。それを防ぐための検査です。
ポートがないと分かったら、以後の出力は捨てます。

送信（`serial_putc`）では、ライン状態レジスタの「送信バッファが空いた」ビットを待ってから 1 バイト書きます。
`'\n'` は、端末で正しく行頭に戻るよう `"\r\n"` に変換します。

## 8. printk と書式化エンジン

`printk` はカーネル版の `printf` です。中身は2つに分かれています。

```text
printk("x=%d\n", 5)            src/printk.c
   └→ format_v(sink, ctx, fmt, ap)   src/lib/format.c（書式化だけを担当）
         └→ sink('x'), sink('='), ...  1 文字ずつ渡す
               └→ serial_putc(c)      src/drivers/serial.c（出力先）
```

**sink 方式**（書式化エンジンが 1 文字ずつ「出力先の関数」を呼ぶ形）にした理由は次の3つです。

- **出力先を差し替えられる**：今はシリアルだけですが、M6 で画面コンソールが加わっても `format.c` は変わりません。
  `ksnprintf`（文字列への書き込み）も、同じエンジンに「バッファに書く sink」を渡しているだけです。
- **ホストでテストできる**：`format.c` はハードウェアにも `kui/string.h` にも依存しません。
  そのため、普通の Linux プログラムとしてコンパイルし、AddressSanitizer 付きで検証できます。
  一部のテストは、ホストの libc の `snprintf` と結果を照合しています。さらに `test_format_fuzz.c` では、
  書式指定と引数を疑似乱数で大量に組み合わせて `snprintf` と突き合わせています（乱数の種は固定なので、失敗は毎回再現します）。
- **メモリ確保が不要**：バッファを確保せずに出力できます。M2 でメモリ管理ができる前から使えます。

対応している書式は `%c %s %d %i %u %x %X %p %%`、フラグ `-` と `0`、幅（数字か `*`）、`%s` の精度、長さ修飾 `hh h l ll z` です。
浮動小数点（`%f`）は、SSE を使わない方針なので対応していません。

`INT64_MIN` のような境界値で未定義動作にならないよう、負の数は絶対値を符号なし整数で計算しています。

## 9. memcpy などを自前で持つ理由と no_builtin の罠

カーネルには C 標準ライブラリがないので、`memcpy`、`memset`、`strlen` などを `src/lib/string.c` に自前で用意しています。

**`-ffreestanding` でも `memcpy` などは必要です。** コンパイラは、構造体の代入や大きな配列の初期化を、
**自分の判断で `memcpy` / `memset` の呼び出しに変換する**ことがあるからです。
これは C の freestanding 環境の約束事で、`memcpy`、`memmove`、`memset`、`memcmp` の4つは環境側が用意しなければなりません。

### 罠：自分自身を呼んでしまう

`memset` を次のように素直に書くとします。

```c
void *memset(void *dst, int c, size_t n)
{
	unsigned char *d = dst;
	while (n--)
		*d++ = (unsigned char)c;   // ← コンパイラが「これは memset と同じだ」と認識する
	return dst;
}
```

最適化が有効だと、コンパイラはこのループを**`memset` の呼び出しに置き換えます**。
すると `memset` が `memset` を呼ぶ無限再帰になり、スタックがあふれてカーネルが落ちます。

対策は二重にしています。

1. `string.c` の各関数に `__attribute__((no_builtin))` を付ける
2. `string.c` を `-fno-builtin` でビルドする（Makefile の `NOSAN_FLAGS`）

ホスト単体テストでは、ホストの libc の `memcpy` と名前が衝突します。
そこで、`KUI_HOST_TEST` を定義したときは `host_memcpy` などの名前でビルドしています（`kui/string.h` の `KUI_STRFN` マクロ）。

## 10. panic と UBSan

### panic（`src/panic.c`）

回復できないエラーが起きたら、`panic("...")` で止まります。

```text
PANIC: selftest
  called from 0xffffffff80001999
```

- 最初に割り込みを禁止します。
- `called from` は、panic を呼んだ場所のアドレスです。`llvm-addr2line -e build/c/kui.elf 0xffffffff80001999` で、ソースの行に変換できます。
- panic の表示中に再び panic した場合（例：表示処理の中で UBSan が反応した場合）は、`PANIC: nested panic` とだけ出して止まります。
- テスト用カーネルでは、CPU を止める代わりに QEMU を「失敗」（終了コード 35）で終了させます。テストが固まらずに失敗として報告されます。

`KASSERT(条件)` は、条件が偽なら panic するマクロです。リリースビルドでも無効になりません。

### UBSan（`src/ubsan.c`）

C には**未定義動作**（Undefined Behavior）があります。
符号付き整数のオーバーフロー、配列の範囲外アクセス、アライメントのずれたポインタなどです。
未定義動作は、その場では何も起きないように見えて、後で原因不明の不具合として現れることがあります。カーネルでは特に厄介です。

`-fsanitize=undefined` でビルドすると、コンパイラは未定義動作になりうる箇所に検査コードを埋め込みます。
違反があると `__ubsan_handle_*` という関数を呼びます。普通のプログラムではコンパイラ付属のランタイムがこの関数を提供しますが、
カーネルにはないので、19 種類のハンドラを自前で実装しました。

```text
UBSAN: add-overflow at src/kmain.c:74:26     ← 種類と、ソースの位置
  'int32_t' (aka 'int')                      ← 関わった型
PANIC: undefined behavior detected (add-overflow)
```

- debug ビルド（既定）でのみ有効です。release ビルドでは外します。
- `ubsan.c` 自身と `string.c` は、検査の対象から外しています。ハンドラの中で再び検査に引っかかると、無限に再帰するからです。
- コマンドライン `selftest=ubsan` で、わざと符号付き加算をオーバーフローさせます。こうして「検出の仕組みが壊れていない」ことを結合テストで確かめています。
  変数を `volatile` にしているのは、コンパイラが計算を省略して検査が走らなくなるのを防ぐためです。

## 11. テストの3層と CI

実装からマージまでを AI が行うので、品質はテストで守ります。M0 で3層すべての仕組みを作りました。

| 層 | 対象 | 動かし方 | M0 の件数 |
|---|---|---|---|
| ホスト単体テスト | ハードウェアに依存しない部分（string、format、cmdline） | 普通の Linux プログラムとして、AddressSanitizer + UBSan 付きで実行 | 47 |
| カーネル内単体テスト（ktest） | カーネル環境で動くこと、boot_info の妥当性 | テスト用カーネル `kui-ktest.elf` を QEMU で起動 | 14 |
| 結合テスト | 外から見た振る舞い（起動、コマンドライン、自己テスト） | 通常のカーネルを QEMU で起動し、シリアル出力を検証 | 4 |

カーネル内単体テストも、QEMU で起動して合否を判定する部分は結合テストと同じランナー（`tests/run.py`）を使っています。
そのため `tests/integration/` には、結合テスト 4 件と、テスト用カーネルを起動する `ktest` ケースの計 5 ファイルがあります。
`make test-ktest` は `ktest` ケースだけを、`make test-integration` はそれ以外を実行します。

### カーネル内単体テストの仕組み

```c
// 書き方の例（実際のテストは kernels/c/tests/ktest/ にある）
KTEST(example_memcpy)
{
	char buf[4];
	memcpy(buf, "abc", 4);
	KEXPECT_STREQ(buf, "abc");
}
```

1. `KTEST()` マクロは、テストの名前と関数ポインタの組（記述子）を **`.ktests` セクション**に置きます。
2. リンカスクリプトが、そのセクションの先頭と末尾に `__ktests_start` / `__ktests_end` という印を付けます。
3. `ktest_run_all()` は、その間を配列として順に実行するだけです。テストを一覧に登録し忘れることがありません。
4. 全部終わったら、QEMU の **isa-debug-exit** デバイス（I/O ポート `0xf4`）に値を書いて、QEMU を終了させます。

| カーネルが書く値 | QEMU の終了コード | 意味 |
|---|---|---|
| `0x10` | 33（= 0x10 × 2 + 1） | 全テスト成功 |
| `0x11` | 35（= 0x11 × 2 + 1） | 失敗あり、または panic |

`ktest_counts_failures` は「わざと失敗する確認が、ちゃんと失敗として数えられるか」を確かめるテストです。
これがないと、どんなバグがあっても全部 PASS と表示される、壊れたテスト基盤に気づけません。
（ログに `ktest:   tests/ktest/test_ktest.c:30: 1 + 1 == 3` などが出ますが、これは意図どおりです。
合否は `ktest: FAIL` の行と QEMU の終了コードで判定するので、これらの行は失敗扱いになりません）

### 結合テスト

`tests/integration/*.toml` に、1 ファイル 1 ケースで書きます（以下は `m0_boot.toml`）。

```toml
name = "m0_boot"
description = "Limine から通常起動し、boot_info を表示して初期化を終えられる"
milestone = "M0"
kernel = "main"                   # main = kui.elf / ktest = kui-ktest.elf
cmdline = ""
timeout = 30
expect = [                        # 正規表現。この順で出ること
    '^Kui 0\.0\.1 \(Tangmen C kernel\)',
    '^bootloader: Limine',
    '^memmap: [0-9]+ entries, [0-9]+ KiB usable',
    '^kui: init complete',
]
forbid = ["PANIC", "UBSAN"]       # 出たら失敗
exit = "any"                      # any / success(33) / failure(35)
```

`tests/run.py` は、ケースごとに QEMU を並列に起動してシリアル出力を照合します。
`exit = "any"` のケースは、`expect` がすべて出た時点で QEMU を止めて合格にします（M0 のカーネルは自分では QEMU を終了しないため）。
ログは `build/c/test-logs/<名前>.log` に保存します。
この形式はカーネルの実装言語に依存しないので、Rust 版でもそのまま使えます。

M0 のケースは `m0_boot`、`m0_cmdline`、`m0_selftest_ubsan`、`m0_selftest_panic`、`ktest` の 5 つです。

### カーネルとコマンドラインの差し替え

テストごとに ISO を作り直さずに済むよう、**SMBIOS（Type 11 OEM String）経由で Limine の設定を渡す**仕組みにしています（`scripts/qemu.py`）。
SMBIOS は、ファームウェアが OS にハードウェアの情報を伝えるための表です。そのうち Type 11 には、メーカーが自由な文字列（OEM String）を入れられます。
Limine は、`limine:config:` で始まる OEM String を見つけると、ISO 上の `limine.conf` より優先してその内容を設定として使います。
QEMU には `-smbios type=11,path=<ファイル>` で渡します。

この方法には1つ落とし穴があります。ISO 上の `limine.conf` では、カーネルの場所を `boot():/boot/kui.elf`
（「設定ファイルがあったパーティション」の意味）と書いています。ところが SMBIOS から設定を渡すと設定ファイルが
ディスク上にないので、`boot():` が解決できず、Limine は「Failed to open executable」で止まります。
そこで SMBIOS 経由の設定では、**`odd(1:):/boot/kui-ktest.elf`**（1 台目の光学ドライブ全体）と書いています。
QEMU には `-cdrom` の 1 台しか光学ドライブを付けないので、これは必ず ISO を指します。

| 起動のしかた | Limine の設定の出どころ | カーネルの指定 |
|---|---|---|
| `make run`（`CMDLINE` なし） | ISO 上の `boot/limine/limine.conf` | `boot():/boot/kui.elf` |
| `make run CMDLINE=...`、テスト | SMBIOS（`scripts/qemu.py` が生成） | `odd(1:):/boot/<ELF 名>` |

### CI

GitHub Actions（`.github/workflows/ci.yml`）で、push と PR のたびに `scripts/dev make ci` を実行します。

1. 開発イメージをビルドする（GitHub Actions のキャッシュあり）
2. KVM を有効にする（使えなければ TCG で動く）
3. `make ci`：clang-format の検査、release ビルド、debug ビルドで3層のテストをすべて実行
4. 失敗したらテストログをアーティファクトとして保存する

## 12. 開発環境

```text
ホスト（WSL2）
 └─ scripts/dev make <ターゲット>
      └─ docker run tangmen-dev:<Dockerfile のハッシュ>   ← .devcontainer/Dockerfile
           ├─ clang / ld.lld / clang-format（カーネルのビルド）
           ├─ qemu-system-x86_64 + OVMF（UEFI で起動）
           ├─ xorriso（ISO 作成）、gdb
           └─ /opt/limine（Limine v11.2.1 のバイナリ）
```

- **`scripts/dev`** は、開発イメージの中でコマンドを実行するラッパーです。Dockerfile が変わるとイメージのタグも変わり、初回実行時に自動でビルドし直します。
  リポジトリは `/work` にマウントされ、ホストと同じ UID で動くので、作られたファイルの所有者はあなたになります。
- **KVM** が使えれば QEMU は CPU を直接使って高速に動きます（`-accel kvm -cpu host`）。使えなければ TCG（CPU をソフトウェアで模倣する方式。`-cpu max`）で動きます。
  `TANGMEN_NO_KVM=1` で、わざと KVM なしにできます。KVM の有無で実行の速さやタイミングが変わるので、
  M3 以降でタイミングに依存するバグを疑うときは、両方で試すと手がかりになります。
- VS Code を使う場合は、`.devcontainer/devcontainer.json` で同じイメージの中に入れます。

| コマンド | 内容 |
|---|---|
| `scripts/dev make run` | QEMU で起動する（シリアル出力が端末に出る。Ctrl-A を押してから X で終了） |
| `scripts/dev make run CMDLINE="selftest=panic"` | コマンドラインを指定して起動する（SMBIOS 経由で設定を渡す） |
| `scripts/dev make debug` | GDB の接続を待つ状態で起動する（`gdb build/c/kui.elf` → `target remote :1234`） |
| `scripts/dev make test` | 3層のテストをすべて実行する |
| `scripts/dev make ci` | CI と同じ検査をする |
| `scripts/dev make format` | clang-format で整形する |
| `scripts/dev make BUILD=release ...` | UBSan なしでビルドする |

## 13. コードの読み方

次の順に読むと、起動の流れに沿って理解できます。

1. `kernels/c/linker.ld`：カーネルがメモリのどこに、どう置かれるか
2. `kernels/c/src/boot/limine.c`：入口 `_start`、Limine とのやりとり、boot_info への詰め替え
3. `kernels/c/include/kui/boot_info.h`：カーネル本体が受け取る情報
4. `kernels/c/src/kmain.c`：カーネル本体の入口
5. `kernels/c/include/kui/arch/x86_64/io.h` → `kernels/c/src/drivers/serial.c`：ハードウェアを直接操作する最初の例
6. `kernels/c/src/printk.c` → `kernels/c/src/lib/format.c`：ログ出力の仕組み
7. `kernels/c/src/lib/string.c`：自前の標準関数と no_builtin
8. `kernels/c/src/panic.c` → `kernels/c/src/ubsan.c`：異常時の動作
9. `kernels/c/include/kui/ktest.h` → `kernels/c/src/ktest.c` → `kernels/c/tests/ktest/`：カーネル内テスト
10. `kernels/c/Makefile` → ルートの `Makefile` → `scripts/qemu.py` → `tests/run.py`：ビルドとテストの流れ

## 14. 設計判断の一覧

| 判断 | 理由 | 検討した代替案 |
|---|---|---|
| Limine（ベースリビジョン 6）で起動 | 64 ビット・ページング有効の状態から始められ、OS の本質に集中できる | 自作ブートローダー（後で置き換える予定）、GRUB + Multiboot2 |
| UEFI のみ、ISO で起動 | 最近の実機と同じ方式。ISO 1 つで済む | BIOS 併用（テストの手間が倍） |
| `boot_info` で抽象化し、物理アドレスとコピーで持つ | ブートローダーの置き換えと、M2 でのメモリ再利用に備える | Limine の構造体を直接使う |
| higher-half（`0xffffffff80000000`）+ `-mcmodel=kernel` | ユーザー空間を下半分に丸ごと空けられる。短い命令が使える | 下半分に置く（後で移動が大変） |
| セグメントを R-X / R-- / RW- に分ける | コードの書き換え、データの実行を即座に検出できる | 1 つの RWX セグメント（簡単だがバグを隠す） |
| 最初の出力先はシリアル | 最も簡単で、自動テストで読める | 画面（フォント描画が必要。M6 で作る） |
| シリアルの存在をループバックで確認 | シリアルのない実機で固まらない | 確認しない |
| 書式化は sink 方式 | 出力先の追加が容易、ホストでテストできる、メモリ確保が不要 | 出力先ごとに書式化を実装 |
| SSE / 浮動小数点を使わない | 起動直後は無効。割り込み時の保存も不要になる | 起動時に SSE を有効化する（必要になったら検討） |
| debug ビルドで UBSan、検出したら panic | 未定義動作を発生源で捕まえる | 警告だけ出して続行（後で原因が分からなくなる） |
| ktest を専用セクションで自動登録 | テストの登録漏れがない | 手で一覧を書く |
| テストの合否は isa-debug-exit の終了コード | 出力の文字列解析より確実 | シリアル出力だけで判定 |
| 結合テストを TOML で記述 | 言語に依存せず、Rust 版でもそのまま使える | テストごとにスクリプトを書く |
| 設定は SMBIOS 経由で差し替え、カーネルは `odd(1:):` で指定 | テストごとに ISO を作り直さずに済む。SMBIOS からの設定では `boot():` が使えない | テストごとに ISO を作る |
| ロック（spinlock）は M1 で入れる | M0 には割り込みも並行処理もなく、競合が起きない | M0 から入れる（使い道がない） |

## 15. 確認問題（自習用）

<details>
<summary>Q1. カーネル本体（kmain 以降）が Limine の構造体を直接使わず、boot_info を経由するのはなぜですか？</summary>

将来ブートローダーを自作に置き換えたとき、変更を `src/boot/` だけに閉じ込めるためです。
また、Limine のデータは後で再利用されるメモリ（bootloader-reclaimable）にあります。カーネル側の静的領域にコピーしておけば、M2 以降も安全に使えます。
</details>

<details>
<summary>Q2. Limine のリクエスト構造体に volatile が付いているのはなぜですか？</summary>

レスポンスへのポインタは、カーネルのコードではなく Limine が起動前に書き込みます。
コンパイラから見ると「初期値 NULL のまま誰も書き換えない変数」なので、`volatile` がないと「response は常に NULL」と最適化される恐れがあります。
</details>

<details>
<summary>Q3. -mno-red-zone を付けないと、どんなときに何が起きますか？</summary>

関数がスタックポインタより下の 128 バイト（レッドゾーン）を一時領域として使っている最中に割り込みが起きると、
CPU が同じスタックに割り込みの情報を積むので、そのデータが上書きされます。割り込みを有効にする M1 以降、まれにしか再現しない破損になります。
</details>

<details>
<summary>Q4. memset の実装に no_builtin が必要なのはなぜですか？</summary>

最適化によって、コンパイラが memset のループを「memset の呼び出し」に置き換えることがあるからです。
そうなると memset が自分自身を呼ぶ無限再帰になります。
</details>

<details>
<summary>Q5. シリアルポートの初期化でループバック検査をするのはなぜですか？</summary>

シリアルポートがない機械では、送信可能を示すビットが永遠に立たず、送信のたびに待ち続けて固まってしまいます。
存在を確かめ、ない場合は出力を捨てるようにしています。
</details>

<details>
<summary>Q6. テスト用カーネルが QEMU の終了コード 33 で終わったとき、カーネルは I/O ポート 0xf4 に何を書きましたか？</summary>

`0x10` です。isa-debug-exit は、書かれた値 v に対して `(v << 1) | 1` で終了します。0x10 × 2 + 1 = 33 です。
</details>

<details>
<summary>Q7. ktest_counts_failures というテストは、何を守るためにありますか？</summary>

テストの仕組みそのものが壊れていないこと（失敗するはずの確認が、失敗として数えられること）を守っています。
これがないと、KEXPECT が何も検査しないバグがあっても、全テストが PASS と表示されて気づけません。
</details>

<details>
<summary>Q8. RSDP のアドレスを boot_info に入れるとき、hhdm_offset を引いているのはなぜですか？</summary>

ベースリビジョン 4 以降の Limine は、RSDP を HHDM 上の仮想アドレスで渡すからです。
boot_info はアドレスを物理で持つ方針なので、変換しています。
</details>
