### 進め方

1. メインが Limine の仕様を調べ、Dockerfile とカーネルのヘッダ（インターフェース）を書いた。
2. オーナーの指示（「時間効率だけを最大化」）により、担当ファイルが重ならないように 4 つのエージェントへ分けて並列実装した。シリアル出力の文言、Makefile のターゲット名、QEMU の終了コードなどの取り決めを全員に共通で渡した。
3. 並行して解説書のエージェントを走らせた。
4. 統合後、観点（カーネル / テスト基盤 / ドキュメント / lib と CI）ごとに 4 つのレビューエージェントを並列で走らせ、各自が担当範囲を直接修正した。

## 振り返り

- インターフェース（ヘッダ、出力文言、make ターゲット）を先に固めてから並列化したことで、4 担当の成果物はほぼそのまま結合できた。ずれたのは開発イメージの依存パッケージと書式の 2 点だけだった。
- 実装担当だけでは見逃したバグ（オーバーフロー、無限再帰、設定注入、GDB 手順）を、観点別の並列レビューがまとめて見つけた。M1 以降も「並列実装 → 観点別の並列レビュー」を標準の手順にする。
- 解説書は実装と並行して書き始めたため、最終状態との食い違いが出た。レビューで直せたが、M1 からは解説書の最終確認をレビュー工程に必ず含める。
- 次の M1 への申し送り：物理アドレス 0 番地が usable で報告される（M2 の物理ページアロケータで除外する）。UBSan の報告に値（lhs / rhs）を出すと調査が楽になる。
